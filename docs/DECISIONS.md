# Decisions

## D1. OCCT bindings: path B, own `cxx` bridge

**Decision.** `rolidium-kernel` contains its own C++ bridge (`cxx`) to Open CASCADE 8.0.1, statically linked.
We do not depend on `cadrum`.

**Evidence.** `cadrum` 0.9.1 was built and its source checked against the 14 capabilities the kernel needs:

| # | Capability | `cadrum` 0.9.1 |
|---|---|---|
| 1 | box, cylinder | yes |
| 2 | planar face from profile with holes | yes (inside `extrude`) |
| 3 | prism | yes |
| 4 | booleans | yes |
| 5 | merge coplanar faces | yes (`clean`) |
| 6 | tessellation with face IDs, edge polylines | face IDs yes, edge polylines without edge IDs |
| 7 | face queries (type, normal, axis, radius, inner/outer loops) | type and axis yes, outer/inner loops not distinguished |
| 8 | edge queries | endpoints only, no type |
| 9 | validity check | **no** |
| 10 | section by plane | **no** |
| 11 | fillet, chamfer | yes |
| 12 | STEP and BREP I/O | yes |
| 13 | sewing | yes |
| 14 | operation history | booleans only |

Path A (cadrum plus a small extra bridge) does not work: `Solid::inner` is private, so our own C++ code
cannot reach the `TopoDS_Shape` of a cadrum solid. The only link would be a BREP round trip per operation,
which loses face identity (needed for selection to survive operations). Also several cadrum paths
`panic!` on native errors, which conflicts with the reliability rule.

**What we reuse.** The prebuilt static OCCT 8.0.1 tarball that cadrum publishes (MIT, built from upstream
OCCT with a fixed recipe). `build.rs` downloads it once into `target/rolidium-occt`, verifies SHA-256
and links it. `ROLIDIUM_OCCT_ROOT` overrides it with a local build. So `cargo build` needs no manual OCCT
installation, only `curl` for the first download.

**Design points of the bridge.**
- Every exported function takes a global lock and converts all exceptions into `Result` errors.
  Meshing mutates shared native shapes, so serialising native calls is the safe choice.
- Shapes are immutable; face and edge identities are indices into the shape's own index maps.
  Identity across operations is carried by explicit `History` links (boolean and USD history merged).
- Every modelling operation validates its result (`BRepCheck_Analyzer` plus "exactly one solid").

## D2. Face/edge identity

A face is identified by its index in the current solid version. After each operation the kernel
returns `History` links (operand, source face, result face) so selection can be remapped.

## D3. Pull on a planar face

Pull on a planar face extrudes the face outline and fuses (outwards) or cuts (inwards). Known limitation
(a first version): sloping neighbours are not extended; a true face offset is planned (see the roadmap).

## D5. OCCT archive source

`build.rs` looks for the archive in `$ROLIDIUM_VENDOR_DIR` (default `~/rolidium-vendor/`, outside git) and only
downloads it if missing. The SHA-256 is verified in both cases.

## D6. Fonts

OFL-1.1 and Ubuntu-font-1.0 (font licenses, they do not affect the program's license) are allowed in `deny.toml`; egui's bundled fonts are back. The program does not depend on system fonts.

## D7. Editing finished rounds and chamfers

Faces made by Round/Chamfer are tracked as `Feature`s through the kernel history, so the marking survives later edits. To change
one, `edit_blend` uses OCCT defeaturing on the current solid (not a rebuild from older steps), then rounds the restored sharp edge
again. Reasons: the document stays a plain list of solids (direct modelling), later operations are kept, and one code path handles
size change and removal. Limits: a feature is edited as a whole (all faces made by one command change together); if the
neighbouring faces cannot be extended (very tight corners) the operation reports an error and changes nothing. Checked on a box with
one edge, four edges and all twelve edges (corner blends).

## D8. Error tone without audio libraries

No Rust audio crate is used (they need ALSA development headers at build time). The tone is generated in the program and handed to
`paplay`, `pw-play` or `aplay` on a separate thread; without them or without a sound device nothing happens. Trade-off: a process is
started per tone (at most twice a second); a native back end can replace this later.

## D9. Translation keys

The English text is the key (no separate id table), so code stays readable and a missing translation shows English. Messages with
numbers are matched by `{}` patterns. A test lists texts missing in the Czech file and another one checks that Czech text appears
nowhere else in the repository.

## D10. Pull mode meaning

`Add` and `Cut` take the size of the distance and force the direction (Add: outwards, Cut: inwards), they do not reinterpret the
sign. The "Distance to opposite face" field always works as a dimension (Auto), also when Add/Cut is chosen; "Up to" is Auto too.

## D11. Crate boundaries

The crates keep clear boundaries so that optional modules can be attached later: `rolidium-cam` stays independent of the app crate, the
document keeps unknown file content (D12) so a build without a module does not lose its data, and modules attach through the
document and commands layer rather than through app internals.

## D12. File format

Zip container with `manifest.json`, BREP per body, JSON per sketch; see `docs/FILE-FORMAT.md`. Approved in advance without changes.
Decisions inside it: ids are stored and kept; face indices of rounds and chamfers are stored with a face-count check; unknown zip entries
and JSON fields are carried through load and save (`Extras`); saving is atomic with a `.bak`; dirty state compares the saved snapshot
(`Arc` pointer) with the current one, so undoing back to the saved state is clean.

## D13. Tangent chain of rounds

The current solution stays: the whole chain that OCCT treats is highlighted. No own blend builder and no patched OCCT.

## D14. Rounds next to existing rounds

Still no own blend builder and no patched OCCT; only the order of existing operations changes. When the tangent chain of a new round
runs through the end arcs of tracked rounds (same kind), those rounds are removed (defeaturing), then every edge the user ever chose
is rounded again in **one** operation, each group with its own radius (`BRepFilletAPI_MakeFillet::SetRadius` per edge), so the
edges beyond the arcs stay sharp. Edges are followed through the operations as pairs of faces, not as edge numbers. Each blend stays a
separate feature (editable and removable). If a step fails, the plain operation runs and the status bar says that the whole chain was
treated; the model is never left in between (one undo step). Chamfers are not tangent to their neighbours, so the chain never runs on and
nothing special is needed; chamfers with different distances cannot be combined and fall back.

## D15. Move, Revolve and visibility

* Move rotates about the centre of the selection's bounding box (or the typed axis) and then translates; sketches drawn on a moved body
  move with it (their plane is transformed), rounds and chamfers follow through the transform history. Copy makes new bodies without sketches.
* Revolve: the axis must lie in the plane of the profile and may touch it, not cut through it (checked on the outline polyline). A sketch
  on a base plane that cuts uses the first body the revolved shape overlaps. Revolve of a flat face is `RevolveFace`.
* Visibility is a property of bodies and sketches (saved in the file). Hidden bodies are not meshed, so they cannot be picked or exported.

## D16. Combine, arcs and angled chamfers

* Combine works on bodies in the document: Merge removes the tools; Cut and Intersect remove them unless "Keep tools". A merge of bodies
  that do not touch and a cut or intersection without overlap are refused with a clear message. A cut that splits the target makes separate
  bodies (their rounds and chamfers are not carried over in that case).
* The arc is stored as centre, radius, start angle and sweep (not as three points); it is built from three points or from the two ends and
  a radius. Regions treat it like a piece of a circle.
* An angled chamfer measures the distance on a reference face chosen by a fixed geometric order of the two faces (not by index), so the
  side survives other operations; Flip takes the other face. Angle and flip are stored with the feature (and in the file). The kernel cannot
  do it on edges whose tangent chain is longer than the selection; this is reported and nothing changes.
* The support address is chosen once per installation (only the index is stored); all three addresses are constants with a bech32 check in tests.

## D17. Loft

Kernel: `BRepOffsetAPI_ThruSections` (solid, ruled or smooth) with `CheckCompatibility`, which lets OCCT align the start points and
directions of the wires so the surface does not twist. A profile with holes: the outer wires are lofted into one solid, each set of
corresponding inner wires into another, and those are subtracted; the number of holes must match. A ruled loft of two coaxial circles
comes out of OCCT as a real conical surface (checked in a test), so nothing special is needed to keep it analytic. The window preview
is not the kernel result but a cheap translucent strip between the aligned, resampled outlines.

## D18. Windows cross-build

Target `x86_64-pc-windows-gnu` with mingw-w64 (posix threads) and the prebuilt Windows Open CASCADE archive of the same project that
supplies the Linux one; the hash is checked the same way. The archive is chosen from `CARGO_CFG_TARGET_*` in `build.rs`, so the build
machine does not matter. `libstdc++` and `winpthread` are linked statically (the exe then needs no extra DLL). The MSVC target was not tried:
it needs the MSVC libraries, which cannot be installed on Linux without Microsoft's licence terms.

## D19. File dialog

One folder browser (`browser/`) serves Open, Save As, Import, Export STEP and Export STL. Folders are read on worker threads and the
window shows a spinner, so a slow disk never freezes it. Places come from `/proc/self/mounts`, the GTK bookmarks file, `user-dirs.dirs`
and the gvfs mount (network shares opened in the file manager). The pure parts (parsing, sorting, filtering, time formatting) have unit tests.
Documents and exports remember their last folder separately.

## D20. Sketch plane move and loft from a selection

The plane is moved by changing the sketch offset, shown as an arrow in the viewport. A sketch on a plane that already holds one gets a new
sketch on the moved plane. Loft takes its profiles in the order they were selected (Ctrl+click); a closed flat loop of one edge is a profile
too (kernel: `LoftInput::Edge`, a planar face built from the wire of that edge).

## D21. Graphics diagnostics and the Windows drawing problems

A report from Windows 10 (grid, axes and committed sketch lines missing, software adapter "Microsoft Basic Render Driver") could not be
reproduced on Linux: the Linux Vulkan and OpenGL backends draw everything, and Wine has no usable GPU path in this environment. Changes that
remove the likely causes without changing the picture on Linux: the grid and thick-line vertex shaders no longer use dynamically indexed
local arrays, and the grid fragment shader has no early return before its derivative calls (uniform control flow). Everything else is
made observable instead of guessed: all graphics errors (validation, pipeline creation, device loss) go to the log; a real adapter beats a
software one; the backend can be chosen (`--backend`, Settings, `ROLIDIUM_BACKEND` for the CLI); `--diagnose` / About > Save diagnostics
write a zip with the adapters, limits, system, log and an off-screen test scene (grid, axes, sketch, body) from every backend; the same
scene with a pixel check is part of `--selftest` and of the render tests. Later the window was verified on real Windows 10 with a Radeon RX 580: grid, axes, sketches and the dark theme draw correctly; the missing grid and sketches were a property of the software renderer.

## D22. Grid reach

Each of six grid levels (minor, major and x10, x100, x1000, x10000 of the major step) fades out per axis when its lines are closer than
8 px on screen, so a coarser level takes over towards the horizon and nothing shimmers. The distance fade is `max(40 x camera distance,
30 x model radius)` (the app passes the model radius in `Frame::scene_radius`).

## D23. Smooth chains, checked rounds

A loft splits its outline into several edges (CheckCompatibility makes both profiles consist of the same number of edges, so a circle
joined to a rounded rectangle is cut into eight pieces) and each piece has its own lateral face, so Open CASCADE does not see the pieces
as a tangent chain and rounding one of them gives a damaged surface. `Solid::smooth_chain` collects the edges that continue each other
with a tangent difference of at most 20 degrees and share a face, by position, and every round and chamfer works on the whole chain.
`check_blend` refuses a result that is invalid, cuts through itself (`BOPAlgo_ArgumentAnalyzer`), grows the outer size or changes the volume
by more than 12 x size^2 x edge length. The division lines of the lateral faces remain: they are real edges between different surfaces.

## D24. Languages and fonts

German, Spanish, French and Japanese were machine translated (all texts including the help cards); a test keeps every language file at the
same keys and placeholders. Noto Sans JP Regular (SIL Open Font License 1.1, `assets/fonts/`) is a fallback font for all languages so that
Japanese file names are shown correctly; it adds about 4.5 MB to the program. The system language also comes from the system locale on
Windows (`sys-locale`).

## D25. Curves, helix and sweep

Curves are document objects (`CurveDef`: a polyline with an optional corner radius, or a helix), numbered in their own series but sharing the id counter
with bodies and sketches (the first version forgot that; a test keeps ids unique). The kernel builds a path wire on demand (`Path`): lines and arcs,
a helix as a 2D line on a cylindrical or conical surface (in pieces of one turn, because one long edge made the sweep 10 times slower) or a chain
of body edges. `Solid::sweep` uses `BRepOffsetAPI_MakePipeShell`; along a helix the profile keeps its orientation to the axis (binormal mode).
Holes of the profile are swept separately and subtracted. The check: valid solid, volume 0.3 to 3 times profile area x path length, no
self-intersection. The general self-intersection check (`BOPAlgo_ArgumentAnalyzer`, now parallel) takes about 18 s on a 15 turn thread, so for a
helix the equivalent test is done directly (the profile must be narrower than the pitch along the axis).
Cancelling a running calculation would need the Open CASCADE call to be interruptible (a progress indicator that is polled); the app shows that it
is computing instead and proposes this for later.

## D26. Face normals

`face_info` took the normal from `gp_Pln::Axis()`; for a plane with a left-handed placement (blends make them) that is the opposite of the surface
normal. It is now the cross product of the placement's X and Y directions, flipped for reversed faces. Everything that sketches on, pulls or snaps to
such a face depends on it.

## D27. Cancellable calculations

Open CASCADE algorithms take a `Message_ProgressRange`; a `Message_ProgressIndicator` whose `UserBreak()` reads one global atomic flag lets the application
stop them from another thread (`rolidium_kernel::request_cancel`). Wired in: booleans (also the subtractions inside loft and sweep), rounds and chamfers,
lofts (`BRepOffsetAPI_ThruSections`), sweeps (`MakePipeShell`), meshing (STL export and the display mesh) and STEP export (`Transfer`). A cancelled call
returns `KernelError::Cancelled`; the document is never touched, because a job only computes a new state that is committed afterwards, so the model is
exactly as before and no Undo step exists. Every job resets the flag when it starts; the checks that cannot be interrupted (validity check, same-domain
unification, self-intersection analysis, file opening and saving) look at the flag before they start. A thread groove cut that takes 650 ms was stopped
152 ms after the request in the test. The indication appears after 0.3 s; the user can turn the view meanwhile because the work is on the worker thread;
a second edit is refused while busy and autosave waits for the idle state.

## D28. Measuring and mass

`rolidium_kernel::measure(Elem, Elem)` gives the shortest distance and its nearest points (`BRepExtrema_DistShapeShape` for any point/edge/face pair),
the angle between straight edges and planar faces (folded to 0..90 degrees), the distance of parallel planes and the distance of the axes of two cylindrical
faces. The tool keeps elements as `MElem` (point, edge or face of a body) so that permanent dimensions can be built from them later. Results are
dropped when the document changes. Material is an optional field of a body (`None` = steel), saved only when chosen.

## D29. Where the time goes

`rolidium-cli times` prints the main operations with their stages. The stages are recorded on the calling thread: inside the native code with a small
timer (`StageTimer` in `bridge.cpp`: boolean, unify same domain, validity check, pipe shell, hole cut, mesh) and in Rust with `timing::stage`. The application
writes the same stages to its log after every operation ("operation: job ... ms, with display mesh ... ms; ..."). Cheap improvements made: `Solid::volume`
now computes only the volume (it used to compute volume, area and the bounding box, about twice the time and 230 ms on a thread), the display mesh asks only for the
bounding box, and the validity check runs in parallel. The pull on a 201-face part is about 110 ms (boolean 35-43, unify 30, validity 30, volume 6); the rest would need an
incremental check or an own unification, see ROADMAP.

## D30. Combine must not lose a body

**The bug.** A spring (a circle swept along a helix on the surface of a cylinder, half sunk into it) was merged with the cylinder: first the program said the bodies do not
overlap, then the spring vanished and only the cylinder stayed. Findings: the swept spring is one closed solid with a positive volume (7 faces for 5 turns: one per
turn plus the two caps; edge tolerance 1e-7, vertex tolerance up to 5e-5, volume equal to pi r2 L within 0.5 %), so the body itself is right. The trouble is in OCCT: (1) a face
that wraps a whole turn around the cylinder made the intersections miss or botch (the path is now cut into pieces of at most half a turn: 0 wrong results of 56 combinations
instead of 10); (2) with the profile on the plane the application uses (normal against the direction of the path) the merge alone is still sometimes wrong (the result is the
cylinder only) while the cut and the common part are right. "First attempt said no overlap, second attempt lost the spring" were the two faces of the same thing: whether OCCT found
no intersection, found a partial one (result in pieces) or classified the spring as lying inside depends on where the seams of the turns fall on the seam of the cylinder and
on the pitch, so two drawings that look alike behave differently.

**What is done.** `Solid::boolean_checked` compares the result with an independent calculation of the volume of the common part (merge = A + B - common, cut = A - common): two
ways must agree; if they do not, other ways are tried (merge as cut then merge, cut as cut by the common part, common as A - (A - B)); when no two agree the operation is refused with
an explanation and the model is unchanged. A slow operation (over 1.5 s) is not repeated: only the volume limits are checked. The limits are also checked on their own (merge at
least the larger input and at most the sum; cut positive and at most the target; common positive and at most the smaller body). "Do not touch or overlap" is said only when
`Solid::distance_to` says the bodies are apart; otherwise the message is that the result does not add up and what to try. Bodies made by sweeping, lofting and revolving are
checked when they are made: one valid closed solid with a positive volume. Result of a way other than the first has an empty history (rounds and chamfers of the target are then
not kept as editable features).

## D31. The MCP server

The MCP server lives in the `rolidium-cli` crate and is started as `rolidium mcp` (see D32 and `docs/MCP.md`). The table of commands (`spec.rs`) is the single source of the script language and of the tools; a
tool call becomes a script line run by `Runner::run_line`. The protocol is written by hand (JSON-RPC over stdio; both the `initialize` and the `server/discover` era). A software
renderer (`soft.rs`) draws the pictures so that no graphics card is needed. Safety: files only under `--root` (symbolic links resolved), no network, no commands, a time limit per
call through the cancellable kernel, limits of sizes and ranges. The messages of the server are in English only (they are read by the model, not by the user).

## D32. One program with three modes

The first packages held three programs (`rolidium`, `rolidium-cli`, `rolidium-mcp`), each with its own copy of the statically linked geometry
kernel, so the package grew from 42 to 58 MB. Options considered:

* **One program with three modes (chosen).** `rolidium` starts the window; `rolidium cli ...`, `rolidium mcp ...` and `rolidium mcp-config`
  run the tools of the `rolidium-cli` crate, which the app crate depends on. One copy of the kernel per package. On Linux the package also
  holds links `rolidium-cli` and `rolidium-mcp` to the program, which select the mode by their name. The dispatch happens at the top of
  `main`, before the logger or the window is touched, so the MCP mode prints nothing to standard output except protocol messages (a test
  checks that the first line the server prints is a JSON answer, also through a link). On Windows the program is built as a window
  program (no console box on a double click); the command-line modes attach to the console of the parent with `AttachConsole`
  (`crates/rolidium-app/src/winconsole.rs`, the only unsafe code of the app crate) only when the standard handles are not valid, so a client
  that starts the server with pipes gets the pipes unchanged. The Windows package has no links, a client uses `rolidium.exe mcp`.
* **The kernel as a shared library next to the programs.** It would also give one copy, but needs the C++ part to be built as a shared
  library with a C interface between Rust crates, loading and path handling in the packages and DLL packaging on Windows. It would make
  relinking against another Open CASCADE easier, which is not needed since the source and `ROLIDIUM_OCCT_ROOT` allow that already (D4).
  Rejected for now because of the effort and the risk.

Release binaries are also stripped of symbols (`strip = "symbols"`); a panic still prints its message, only backtraces lose function names.

## D33. Safe start of the graphics

A driver can kill the process by merely being loaded (seen: the Vulkan driver of Intel integrated graphics, `igvk64.dll`, exception
0xc0000005, at every start of 0.2.0 on one Windows machine, while DirectX 12 worked). Nothing in-process can catch that, so the start is
defended from outside. (1) `auto` is a list of steps with one backend per instance (`rolidium_render::auto_order`): on Windows DirectX 12 with a
real card, Vulkan with a real card, OpenGL, then software adapters; elsewhere one step as before. A probe of a step creates the instance and
lists the adapters before the window library does it again, so a crash happens in the program's own code where it is logged. (2) A marker
file per process in the state folder, held under an exclusive file lock: the system releases the lock when the process dies, so a marker
that can be locked but still exists is a start that did not get through, while a locked one belongs to a running program (another window)
and is left alone; markers of other versions are ignored; a normal exit, a closed window and the first five drawn frames remove the
marker. A failed backend is stored in the settings (`backend_blocked`), skipped by `auto` and shown once; `auto` in the settings or
`--backend auto` forgets it. Rejected: skipping on the first sign of trouble for an explicit choice (an explicit choice initialises exactly
that backend). Only graphics errors (not a missing display) count against a backend. (3) The log flushes every graphics step to the disk;
on Windows an unhandled-exception filter (the only other unsafe code besides the console attachment) adds one line. (4) The diagnostics run
each backend in a child process with a time limit. On Linux the order is unchanged and a stale marker never blocks anything.

## D34: Fill makes a sketch, and a plug up is a body of its own

Fill turns a closed flat loop of edges into a sketch with a region (`Command::FillLoop`), from the exact curves (lines, circles, arcs; the
centre and axis of a circle come from the kernel, `edge_geom` in the bridge). The sketch is marked `fill`: pulling its region always adds
material, in the direction of the sign (inwards closes the hole, outwards makes a plug). A plug pulled outwards from a hole of the same
radius touches the body only along a circle, and a solid cannot be made of a contact along a line, so the kernel refuses to fuse it
(`SplitResult`); the plug then becomes a body of its own and the user is told. The same holds for a new volume that touches a body only along
an edge or at a point (A.7: any other contact, by a face or an overlap, is joined to the body).

## D35: Join ends pairs free ends from the closest pairs

A free end is an end that touches no other end (1e-6 mm). Free ends are paired greedily from the shortest distance, each end at most once,
up to a largest gap; the ends of one line are never paired together. Below 0.01 mm both ends move to their middle point (an arc is drawn
again through its other end, its middle and the new end), above it a line bridges the gap. 3D lines are merged into one polyline. The core is
in `rolidium-sketch/src/join.rs` and is shared by the window, the CLI and the MCP server.

## D36: Display meshes follow the zoom

The display mesh is made for a pixel size: the deviation of the triangles and of the edge polylines (from exact curves with an adaptive
tangential deflection) is 0.4 of a pixel (superseded in D37 for the angle and the caps). When the view has been still for 0.35 s and the meshes
were made for a pixel more than 1.4 times larger (or 4 times smaller), the worker makes them again; the result is dropped when the model
changed meanwhile, and a running remesh is cancelled when an operation starts. At most 1.5 million triangles per body and 3 million in all
(the deflection is raised when an estimate from the previous mesh passes the cap). The kernel, measurements and the STL export do not use
these meshes.

## D37: Rough first display, in-view faces refined within a budget

After an operation a body is shown at once with a rough mesh (deflection 0.2 % of its size, about 2 pixels of a 900 px window); the refinement for the zoom
comes later in the background. The angular limit of the display meshes is 0.5 rad and only a safety limit: the density is set by the deviation in pixels, so a
shape that is small on the screen is not made denser than its size asks for (0.12 rad had made the spring 3 times slower). When the view is zoomed in, only the
faces whose box meets the view are meshed again (`Solid::view_mesh_faces`: the rest is taken from the present mesh, the edges of the faces in view are made
again); they get at most 60 000 new triangles and the whole mesh stays under 150 000 per body (600 000 in all), which keeps the work for a part like the
spring within about 1.5 s. When the cap is reached the deviation is larger than 0.4 pixel (the spring at 100x: about 7 pixels) - the honest limit of
meshing whole faces; the next step would be to cut the faces to the view.

## D38: The demo models are built from parts that are moved into place

Pull joins bodies that touch, and Revolve turns about an axis through the origin, so the demos (`examples/demos`) build every part in an empty place (the
staging area, or the origin for revolved parts) and move it: a move never joins bodies. Python scripts (`rdm.py`, `parts.py`) write the scenarios; the program runs the
scenarios (`build.txt`). A cut of a sketch on a plane first compared every body with the cutting volume by the exact distance (seconds each on parts with many
faces); a test of the boxes now comes first (`Solid::may_be_within`), which made the building of the router 15 times faster.
